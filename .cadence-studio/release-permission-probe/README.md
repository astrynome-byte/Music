# Probe CI réversible de permission tag + brouillon privé

**Préparé uniquement, jamais exécuté contre GitHub ici.** Ce lot ne publie pas le logiciel, ne crée aucun installateur et ne rend aucune release publique. Il ne touche jamais `main`. Seuls un tag temporaire et une release privée draft+prerelease vide peuvent être créés dans la future exécution, avec le seul `GITHUB_TOKEN` éphémère `contents:write/actions:read`. Aucun PAT, droit élargi, installation de dépendance ou désactivation de sécurité n’est demandé.

Le workflow Ubuntu24.04 s’active uniquement quand son propre namespace est poussé sur `cadence-studio/windows-build`. Il commence par les tests de données, puis appelle `python3 -I probe.py --output "$RUNNER_TEMP/release-permission-probe"`. Ce dernier exige un runner hébergé Linux, le dépôt/événement/ref exacts, le vrai GITHUB_SHA40hex, les identifiants de run/attempt et un checkout de ce SHA. Si `ruby`, `git` ou `gh` manque, il refuse avant toute mutation, sans installation.

Avant de créer quoi que ce soit :

1. Lecture API de `main`, qui doit être encore `a6c90b63344b3fd60567fd9f001ac9ecba4b2081` ; son répertoire workflows doit contenir seulement `android.yml` au blob `ad0539f630eb11556f33f487e145d97558a629ff`.
2. Lecture de **tous** les workflows Git de HEAD (≤128,256KiB chacun,8MiB au total) sans exécuter leur contenu ; même blob Android requis. Les octets sont comparés à leur identité Git.
3. Analyse Ruby/Psych standard avec `YAML.safe_load`, sans objets permis, aliases ou évaluation ERB ; profondeur bornée, doublons de mapping refusés. Le nœud AST doit contenir un unique `on` littéral. Si Psych le transforme en clé booléenne `true` (YAML1.1), cette clé est analysée explicitement ; aucun déclencheur n’est ignoré.
4. Refus de `release`, `create`, `delete`, `workflow_run`, événements inconnus et `push` sans `branches:[...]` explicites. Aucune présence de `tags`, `tags-ignore` ou `branches-ignore` n’est admise. Les événements indépendants connus PR/PR-target, dispatch manuel, appel et schedule sont permis ; ils ne sont pas déclenchés par les opérations du probe. L’inventaire des blobs/événements est conservé.
5. Absence du tag unique `cadence-studio/qa-permission-<run_id>-<attempt>` vérifiée par GET404. `main` est relu immédiatement avant les créations du tag et du brouillon.

Le tag pointe uniquement sur le **GITHUB_SHA courant** du probe, puis un POST structuré crée un brouillon privé+prerelease au même tag, sans asset. Son ID doit être fourni par la réponse de création et sa nature privée/vide est revérifiée par GET de cet ID. Aucun `edit/publish` n’existe dans le script. Ce test mesure cette capacité avec un tag existant créé au SHA courant ; il ne qualifie pas la création future d’une release au commit producteur ancien ou sans tag préexistant.

Un `finally` tente de supprimer seulement l’ID renvoyé par son propre POST, après contrôle de tag/draft/prerelease/absence d’assets, et seulement le tag temporaire si son SHA est toujours le GITHUB_SHA attendu. Il confirme ensuite par GET404. La valeur de `main` est relue aussi immédiatement avant chaque DELETE. Si elle change, le nettoyage est refusé et signalé avec les identifiants possédés, afin de ne pas émettre des événements de suppression sur un état de workflows non audité ; une reprise manuelle contrôlée sera nécessaire. Si l’issue d’un POST de brouillon est inconnue sans ID retourné, aucun brouillon n’est effacé par recherche de nom ; le rapport signale explicitement l’incertitude. Une coupure brutale du runner peut empêcher le `finally` ; les reçus déjà disponibles et le namespace unique permettent une reprise manuelle contrôlée, sans suppression globale.

`permission-probe-report.json` et les marqueurs `CADENCE_RELEASE_PERMISSION_PROBE_*` distinguent : refus préflight, refus/échec du tag, refus/échec du brouillon, capacité effectivement observée puis retirée, ou nettoyage échoué. Les statuts HTTP et codes gh sont observés ; aucun en-tête, environnement, token ou corps d’erreur arbitraire n’est imprimé. Les appels gh sont des listes d’arguments, JSON sur stdin, hôte fixé github.com, délais30s et sortie bornée. Une réponse GET404 est un contrôle d’absence accepté même si gh termine avec code1.

Vérification locale : `python -m unittest -v test_probe.py`. Quinze tests de données ont passé (règles des déclencheurs, lecture du format HTTP, suppressions possédées et refus si identité change), deux tests du vrai parseur Ruby sont **ignorés ici car Ruby n’est pas installé**. Ils s’exécuteront sur Ubuntu si Ruby est présent. Aucun HTTP réel, tag, draft ni publication n’a été utilisé pour ces tests. La syntaxe Ruby et la capacité effective du token restent à confirmer par la première exécution du workflow ; un échec ne constitue pas une validation du produit.
