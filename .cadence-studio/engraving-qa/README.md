# Qualification préparée du moteur de gravure Windows

État : **préparé, non publié, non exécuté sur Windows**. Ce jalon utilisera les vrais GoogleTests amont ; aucun résultat PASS du moteur Cadence n’est encore revendiqué. Il ne construit ni installateur ni application cadeau et ne modifie aucun moteur ou test amont.

Le workflow `cadence-engraving-qa.yml` est indépendant des builds APP. Il reconstruit avec le Bootstrap existant de `.cadence-studio/library-source` la source candidate `76b51af495b721776945717a812e1de2394a689a`, arbre exact `59d63e6f93b3bb7e8e5291cf57f57f9c5d61a06b`, depuis MuseScore `v4.7.6` / `96480d58445e3b24b230a3fe7d4725d639aa2eb3`. Toute dérive de cet arbre, du résultat Bootstrap ou des dépendances Windows verrouillées fait échouer la préparation. Le namespace `library-source` doit déjà être présent dans la branche du driver ; son contenu n’est pas remplacé par cette proposition.

Environnement prévu : runner jetable `windows-2022`, MSVC 2022 x64, SDK Windows `10.0.26100.0`, Qt `6.10.2` et mêmes modules que le build complet, CMake `3.31.6`, Ninja `1.11.1`, Python `3.12`, dépendances et SDK ASIO/VST verrouillés par les scripts existants. La version mineure effective de MSVC et Git reste celle de l’image du runner : elle doit être observée dans les logs/runtime, pas annoncée comme figée. Le runtime ASAN est un prérequis de test du worker, sans obligation d’installation pour le destinataire du cadeau.

## Configuration effectivement demandée

`Run-EngravingQa.ps1` appelle CMake avec `MUSESCORE_BUILD_CONFIGURATION=utest`, `MUSE_COMPILE_ASAN=ON`, `MUSE_ENABLE_UNIT_TESTS=ON`, `MUE_BUILD_ENGRAVING_TESTS=ON`, puis **seulement** `cmake --build ... --target engraving_tests --parallel 2`. Aucun `cmake --install` ni build de la cible application n’est demandé. `SetupConfigure.cmake:270` active réellement les tests et ASAN et désactive notamment shell, lecture, MIDI, VST et Autobot ; passer `MUSE_COMPILE_ASAN=OFF` ne serait pas une solution correcte, cette configuration peut l’écraser.

La configuration de compilation choisie est `RelWithDebInfo`, avec lien `/DEBUG /INCREMENTAL:NO`. C’est une adaptation explicite à MSVC : le Debug CMake standard introduit `/RTC1` et le lien incrémental, incompatibles avec AddressSanitizer. ASAN reste activé, sans suppression des erreurs de type `new_delete_type_mismatch` ; `ASAN_OPTIONS=halt_on_error=1`. L’amont Linux utilise habituellement `utest` + Debug dans `buildscripts/ci/linux/build_utest.sh`, puis `ctest -V` dans `runutests.sh` ; ces scripts dépendant de `$HOME/build_tools` ne sont pas lancés aveuglément sur Windows.

Le préflight exige que `vswhere` trouve le composant `Microsoft.VisualStudio.Component.VC.ASAN` dans l’installation active et que sa DLL x64 `VC/Tools/MSVC/<version>/bin/Hostx64/x64/clang_rt.asan_dynamic-x86_64.dll` soit présente. Absence : statut **blocked_prerequisite**, jamais ASAN désactivé ou résultat inventé. Son chemin et son SHA-256 sont enregistrés. Après configuration, les vraies commandes de compilation des cibles engraving/engraving_tests doivent toutes contenir `/fsanitize=address`. Le premier démarrage du binaire lors de la découverte vérifiera ensuite concrètement la résolution des DLL. Cette disponibilité n’a pas encore été éprouvée sur un runner Windows.

Les comparaisons amont (`src/engraving/tests/utils/scorecomp.cpp:56`) appellent `diff -u --strip-trailing-cr`. Le script utilise `usr/bin/diff.exe` du Git for Windows déjà installé, vérifie `--version` puis une comparaison CRLF/LF avec l’option réelle. Il ajoute son répertoire **en fin de PATH**, après MSVC : Git fournit aussi un `link.exe` incompatible avec le linker C++. Le chemin du linker actif est vérifié avant et après les ajouts. Si GNU diff est absent, le préflight est bloqué ; aucun outil de remplacement non vérifié n’est utilisé. Qt et la DLL ASAN sont résolus dans le PATH du processus de QA, restauré en fin de script.

## Onze cas retenus, sans wildcard

`selection.json` donne les noms exacts, les fichiers et les objectifs. `verify.py source` relève dans la source retenue la déclaration `TEST_F`, son numéro de ligne et le SHA-256 du fichier. Les dix cas du plan éditeur sont conservés ; le onzième est `Engraving_CopyPasteTests.copypaste06` (majuscules **CopyPaste**), qui colle une mesure contenant une liaison de prolongation et compare le MSCX attendu.

Les cas couvrent : hauteurs, transposition, limites, notes longues et durées liées, changement de voix/annulation, respiration/annulation/rétablissement, portées liées, modification depuis une partie, saisie depuis quatre parties et sauvegarde/destruction/réouverture avec silences multimesures. Le cas `inputFromParts` a des assertions ciblées sur les accords du conducteur ; il ne compare pas tous les attributs musicaux. Le cas `undoChangeVoice` teste l’annulation, sans redo. `testMMRestLinksRecreateMMRest` est bien une vraie réouverture du fichier écrit ; les intitulés `styleScoreReload` et `TupletTests.saveLoad` ne suffisent pas à prouver cette opération et ne sont pas utilisés à cette fin.

Après compilation, `ctest --show-only=json-v1 -R '^engraving_tests$'` identifie le véritable exécutable. Il est lancé avec `--gtest_list_tests` et le filtre composé des onze noms exacts. Le parseur exige exactement la même liste, sans doublon ou nom `DISABLED_`. La découverte n’est pas un test réussi. Ensuite, CTest exécute seulement son entrée `engraving_tests` avec ce `GTEST_FILTER`, délai de 600 secondes pour le binaire et workflow limité à 120 minutes.

Le succès exige simultanément : retour CTest nul, fichier GoogleTest XML comprenant exactement les onze noms attendus, onze cas `status=run` et `result=completed`, zéro failure/error/skipped/disabled et onze tests déclarés à la racine. Zéro test, liste partielle, cas ignoré, crash et rapport absent échouent. Deux rapports XML sont conservés : le XML GoogleTest avec ses onze cas et le JUnit CTest avec l’entrée agrégée `engraving_tests`, en plus du JSON de synthèse, des listes découvertes et des logs. La durée réelle de compilation reste à mesurer ; le délai du workflow peut bloquer cette première qualification sans constituer un défaut musical.

## Portée et artefacts

`src/framework/testing/gmain.cpp:38` crée une `QGuiApplication`, mais `src/engraving/tests/environment.cpp:48` impose `MScore::testMode=true` et `MScore::noGui=true`. Le worker utilise donc volontairement Qt `offscreen` : il vérifie le modèle natif et sa sérialisation, **pas** les gestes clavier/souris, les palettes, la fenêtre de l’éditeur, le son, les plugins, l’écoute ou l’installation. Les fichiers de référence sont lus dans le checkout ; les sorties de comparaison sont écrites dans l’arbre de build séparé. Le checkout doit rester propre après les tests.

Les logs, cache CMake, commandes de compilation et rapports sont retenus 14 jours dans `cadence-engraving-qa-<run>-<attempt>`. Ce sont des preuves de test, pas un paquet téléchargeable pour le cadeau. La production d’un exécutable de test ne suffit pas : seule une future exécution Windows avec les onze assertions passées permettra d’ajouter ce jalon à STATUS.

Validation locale de préparation : vérification des onze déclarations de la source candidate et de leur inclusion CMake, syntaxe Python/PowerShell/YAML, et contrôles du validateur contre listes/XML synthétiques complets, vides, partiels, ignorés et en échec. Aucun test de gravure n’a été exécuté par ces contrôles de préparation.
